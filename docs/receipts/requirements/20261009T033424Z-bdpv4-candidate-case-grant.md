## Candidate C: driver-issued case grant

### Exact candidate sentence (BDPv4)

A driver may grant a named, authenticated counsel or auditor read-only access to specific imports and submissions of their own for one case, through a revocable, expiring case grant that lists the allowed operations. Without a valid grant, only the driver can verify, analyze or export that data. A grant is not a role, never covers another driver's data, and never decrypts a sealed record. Decryption stays on the escrow and HSM legal-process path, whose custodians act under court process, not under a case grant.

### Proposed ids (PROPOSED, not created)

| Kind | Proposed id | Role |
| --- | --- | --- |
| FR | **FR-RIDE-079** | Functional rule: driver-issued, case-scoped, revocable, expiring read-only grant to a named, authenticated grantee |
| TR | **TR-RIDE-SEC-004** | Technical: grantee principal, grant model, issuance, scope enforcement at every data sink, expiry, revocation and use logging. SEC-002/003 were killed and are not reused. |
| TEST | **TEST-RIDE-058** | Grant happy paths and fail-closed negatives, including scope binding and logging |

### Proposed acceptance criteria (for AGREE with the sentence)

FR-RIDE-079:

1. A grant names one grantor (the driver), one grantee principal, one case id, an explicit list of the grantor's own **import ids** and **submission ids**, the allowed operations, and an expiry. The allowed operations are drawn from: `verify`, `coverage`, `online-hours`, `incident-window` and `package-export`.
2. A grantee call succeeds only when all of these hold: the authenticated caller is the named grantee, the case id matches, the operation is allowed, the grant is neither expired nor revoked, and every row read is in the granted import or submission list. Every other grant-scoped call fails closed with `TENANT_ISOLATION` and returns no data. Calls that TR-RIDE-SEC-004 AC 7 authorizes independently of a grant follow their own rules.
3. Analysis and export results contain only rows whose import id is granted (coverage dictionary, online-hours, trips, scores, locations) and only granted submissions. A wide time window never pulls in an ungranted import. A `package-export` for UC-RIDE-007 carries the selected interval, and rows outside it are excluded. The interval is half-open, `[start, end)`, which matches `AnalyzeIncidentWindow` today: trips are selected by start time and scores by observation time. Inclusion for each dataset:
   - point rows (scores, locations) are included when their timestamp `t` satisfies `start <= t < end`;
   - span rows (trips, online-hours) are included when their start is in `[start, end)`. Such a row is exported whole. If it ends at or after `end`, it is flagged `extends_beyond_interval`. A row that starts before `start` is excluded, even if it overlaps;
   - submissions are included by `collection_unix_millis` under the point rule;
   - import-level rows are included only for an import that contributes at least one included row. These are the coverage dictionary, unverified rows and consents. A consent's timestamp is the import time `IngestPipeline` assigns, not the evidence time, so the point rule never applies to it. A grantee package never contains the identity datasets of the driver's own access export (every `account/` entry: account, vehicles, vehicle versions, profiles, sessions) or the subject access log (`data/access-log.json`), because a grant cannot name them. Its `data/receipts.json`, `manifest.json`, `provenance.json` and `provenance.csv` list only granted submissions and imports.
4. The driver can revoke a grant at any time. Revoked or expired grants fail closed.
5. A grant never authorizes decryption, a working copy, escrow release, or any record of another driver.
6. Each successful grant use is recorded once with grant id, grantee principal, case id, operation, and the import and submission ids returned. Each refused grantee call, and each refused grant issuance or revocation, is recorded with grant id (if any), caller, operation and refusal reason.
7. The driver's own access needs no grant. A driver principal acting on their own data keeps today's own-submissions authorization.

TR-RIDE-SEC-004:

1. Grantees authenticate as their own principal kind (grantee account). Grants reference that principal. A grant secret alone never authorizes a call.
2. Grants are stored with the grantor's driver id. Issuance and revocation accept only that driver's principal. Issuance rejects any import or submission id the grantor does not own. A refused issuance or revocation changes no grant state.
3. Scope is checked server-side on every call, before any data is read: grantee principal, case id, operation, expiry, revocation, and the import and submission lists. Each sink (coverage dictionary, online-hours, trip index, scores, location rows, access-export ZIP, verification report) filters to the granted ids.
4. Use and refusal records are append-only and include the fields in FR-RIDE-079 AC 6.
5. Desktop viewer (UC-RIDE-018, 019 and 026). The viewer identifies the caller by an authenticated principal (driver or grantee), not by a free-text reviewer role as `CourtViewer` takes today. On the Grantee path it shows a record of a bundle only after an online check with the server confirms that the grant is valid (not expired, not revoked), names this grantee and case, allows `verify`, and lists that record's submission. Records the grant does not list are withheld, even when they are in the same bundle. The server, not the bundle, decides which submission a record is: the viewer sends the content hash it recomputes from the sealed ciphertext plus the record's receipt, and the server resolves the submission id from its custody journal. Any submission id or label carried in the bundle is ignored, and a record whose hash matches no submission of the grantor fails closed. Every field the viewer displays for a record must be bound to that resolved submission: telematics cues, GPS and OBD2 presence, admission state and the OTS proof (today `ReviewRecord.Telematics`, `GpsPresent`, `Obd2Present`, `Admitted` and `Ots`, which `TimelineBuilder` renders straight from the bundle). A field is bound when the content hash covers it, when it matches a digest the server returns for that submission, or, for admission state, when the server supplies it. The verified core is shown only when the bundle's receipt core, deterministically encoded, has the digest `receipt_core_digest`. A receipt rebuilt with the same content hash but other metadata withholds the whole record with a refusal record. The OTS proof is bound only after it verifies against the receipt-core digest, the check `AnchorProofVerifier` makes: the proof envelope's `receipt_core_digest` equals SHA-256 of the bundle's deterministically encoded receipt core, which must already equal the server's `receipt_core_digest`, and the sealed ciphertext hashes to the resolved content hash. Its digest must also equal the stored-proof digest the server returns for that submission. A different proof that is valid for the same digest is not the custody proof and is not shown. An unbound field is not displayed, and its withholding writes a refusal record. The Driver path uses the same server resolution: each record must resolve to a submission the authenticated driver owns, or it is withheld and a refusal is recorded. Holding a copied bundle never makes another driver's record "own data". The field-binding rules above apply on both paths. `bundle.CaseId` is never shown, logged or carried as authoritative. On the Grantee path, the case shown, logged and carried into any working copy is the case from the grant context, which `ResolveViewerRecords` echoes back. If the bundle names another case, the record is withheld and a refusal is recorded. On the Driver path there is no grant. Submissions carry no case today, so `ResolveViewerRecords` returns no case, and the viewer labels the case "not server-attested" and leaves the bundle's label out of display and logs. A working copy carries only the `case_id` of the court release that authorized it, as the server holds it. If the server cannot be reached, the Grantee path fails closed, and so does the Driver path for any record it cannot resolve. Each viewer check writes the use or refusal record in AC 4. When the server is unreachable, the viewer writes the refusal to a durable, append-only local outbox and uploads it to the server's refusal log on the next successful connection. Limit: the grant controls what RideAudit software shows. It cannot stop someone who already holds a copied bundle from recomputing ciphertext hashes with other tools. Plaintext stays behind the escrow release in every case.
6. A grantee principal has no write path. These mutating RPCs refuse it with `TENANT_ISOLATION` before any state change, and each refusal writes a refusal record:
   - `Identity.RegisterVehicle`, `UpdateVehicle` and `PutConfigurationProfile`;
   - `Ingest.IngestPrivacyExport`, `IngestThirdParty` and `RecordManualScore`;
   - `Privacy.RequestDeletion`;
   - `Admission.OpenSession`, `SubmitSealed` and `UploadSealedChunk`;
   - grant issuance and revocation (AC 2), and the other grant-management mutations: `Grants.InviteGrantee` and `Grants.DisableGrantee`. The only grantee mutations are the calls AC 7 authorizes independently of a grant: `AcceptInvitation`, `CloseAccount`, `UploadViewerRefusals`, and the court-path `RequestCourtRelease` and `OpenExpiringWorkingCopy`. Each changes only the caller's own state or records.

   `Escrow.RequestCourtRelease` and `OpenExpiringWorkingCopy` are authorized only by the court legal-process path, never by a grant (FR-RIDE-079 AC 5; see the exceptions under AC 7). `ApproveCourtRelease` is refused to every grantee; it accepts only custodian principals.

7. Every RPC refuses a grantee unless it is mapped below to an operation the grant allows, or listed below as authorized independently of a grant. The mapping is:

   | Operation | RPC |
   | --- | --- |
   | `verify` | `Counsel.BuildVerificationReport`, `Escrow.VerifyForCounsel`, `Grants.ResolveViewerRecords` (Grantee path; the Driver path needs no grant) |
   | `coverage` | `Counsel.AnalyzeCoverage` |
   | `online-hours` | `Counsel.AnalyzeOnlineHours` |
   | `incident-window` | `Counsel.AnalyzeIncidentWindow` |
   | `package-export` | `Privacy.RequestAccessExport`, filtered per AC 3 |

   A grant authorizes only the mapped calls above. These calls are authorized on their own terms, independent of any grant:
   - `Grants.UploadViewerRefusals` needs no currently valid grant, because it reports refusals that often arise from expired, revoked or missing grants. It accepts only refusal entries about the caller's own attempts, and it returns no data.
   - `Grants.ListMyGrants` lists only grants naming the caller: grant id, grantor, case, operations, expiry, and the granted `import_ids[]` and `submission_ids[]` (metadata, no data). A grantee learns from it the grant ids it must present in `GrantContext` and the ids it may request.
   - `Identity.CloseAccount` lets an authenticated principal close their own account (see "Public contracts"). It refuses a custodian that still holds an effective slot on an escrow key (see "Custodian principals"). It also refuses a driver for now. Closing a driver account waits on the owner's open DSAR decision (deletion closes the account, or a separate closure request does), and that decision must define what happens to the driver's grants, imports, identity records and submissions. Until then a driver keeps the access-export and deletion rights of FR-RIDE-010.
   - `Grants.AcceptInvitation` lets an existing grantee accept an invitation addressed to its own registered email (see "Public contracts"). It returns no data.
   - `Escrow.RequestCourtRelease` and `OpenExpiringWorkingCopy` follow the court legal-process path (UC-RIDE-011, with the escrow binding in "Public contracts"). A grantee who is the authenticated requester under court process may use them on that authority, never on a grant's. `ApproveCourtRelease` accepts only custodian principals.

   All other read RPCs refuse a grantee with `TENANT_ISOLATION`, return no data, and write a refusal record. These include `Identity.ListVehicles`, `GetConfigurationProfile`, `Admission.GetAdmissionStatus`, `Escrow.GetEscrowStatus`, `Privacy.ViewLocations`, the driver-only `Grants.ListGrants` and `Grants.ListInvitations`, and the custodian-only `Escrow.GetPendingRelease`.

8. Grant transport. Every grantee call carries an authoritative grant context, `GrantContext {grant_id, case_id, idempotency_key}`, as a request field on each mapped RPC. `Privacy.RequestAccessExport` also gains an optional `interval {start_unix_millis, end_unix_millis}` field. A UC-RIDE-007 incident package sets it, and rows outside it are excluded. A UC-RIDE-021 portable export leaves it unset and covers the whole granted scope. `Counsel.VerificationReportRequest.case_id` is deprecated: if it is set, it must equal `GrantContext.case_id`, or the call is refused. This is a contract change: a `GrantContext` message is added to each request in the AC 7 map, and the minor contract version is bumped. The server authorizes against that one grant only. It never infers a grant from the caller and never unions several grants. A grantee call without a grant context, or whose grant id is not the caller's, is refused with `TENANT_ISOLATION`. The use or refusal record names the presented grant id. The `idempotency_key` in `GrantContext`, and the same field on each grant-management request (`IssueGrant`, `RevokeGrant`, `InviteGrantee`, `DisableGrantee`, `AcceptInvitation`), and a top-level `idempotency_key` on every other request a grantee can send that writes a use or refusal record (a mapped call sent without a grant context, and every RPC that AC 7 refuses to a grantee), is client-generated, with at least 128 random bits. The server keeps `(caller, idempotency_key)` with a digest of the request and the id of the use, refusal or management record it wrote, for at least 24 hours. The server never stores the response of a data-returning call. A retry of one runs the call again under the grant and the data as they stand now, so rows deleted since the first call, or a grant revoked, expired or disabled since, are never returned again. A retry that still succeeds writes no second use record. A retry that now fails returns `TENANT_ISOLATION` with no data and writes one refusal record, kept against the key, and later retries with that key write nothing more. Any other retry with the same key and the same request (a management call, or a call that was refused) returns the original outcome and writes no new record. When the response to `ApproveCourtRelease`, `CloseAccount` or `OpenExpiringWorkingCopy` is lost and the caller retries, the retry returns the original outcome or a clear refusal, and the action never takes effect twice: an approval counts once and an account closes once. A lost `OpenExpiringWorkingCopy` response never costs the requester an approved working copy: until the working copy's expiry, the same requester can obtain it again, each delivery is logged, and no plaintext is kept between deliveries. How this is achieved belongs to the escrow slice's contract step. The same key with a different request is refused with `VALIDATION_FAILED`. When a mapped call carries both a top-level key and a grant context, the two keys must be equal. A grantee request with no key is refused with `VALIDATION_FAILED` and writes one refusal record marked `no_idempotency_key`. That is the only refusal the server cannot deduplicate. Driver-path calls are unchanged. `RegisterGrantee` and `RegisterCustodian` also carry `idempotency_key`, but under the registration-retry rule in "Public contracts", not this one. One subject rule covers the legacy fields `driver_id` (on `AnalyzeCoverageRequest`, `AnalyzeOnlineHoursRequest` and `AnalyzeIncidentWindowRequest`) and `subject_driver_id` (on `AccessExportRequest`). With a grant context, the subject is the grant's grantor, and the legacy field must be empty or equal that grantor. Without one (Driver path), the subject is the authenticated driver, and the field must be empty or equal that driver. Any other value is refused with `TENANT_ISOLATION` before a sink reads anything.

TEST-RIDE-058:

1. Happy paths: a granted `verify`, `coverage`, `online-hours`, `incident-window` and `package-export` each succeed for granted data and write exactly one correctly attributed use record (grant id, grantee, case, operation, returned ids).
2. Scope binding: with granted import I1 and ungranted import I2 from the same driver, a wide incident window, online-hours and coverage return only I1 rows. `package-export` contains only I1 and granted submissions. An interval-bound `package-export` (UC-RIDE-007 step 3), requested through the public `Privacy.RequestAccessExport` gRPC call with the interval field, contains no row outside the interval, even from a granted import, and contains no `account/` entry and no `data/access-log.json`. Its `data/receipts.json`, `manifest.json`, `provenance.json` and `provenance.csv` list only granted submissions and imports. The driver's own access export still carries the account entries, the access log, and every submission and import. The boundary cases follow AC 3:
   - a score at exactly `start` is included, and one at exactly `end` is excluded;

### Public contracts (proposed; revised through r33)

These come with the same minor contract-version bump as `GrantContext` (TR-RIDE-SEC-004 AC 8).

- **Grantee accounts.** The driver invites a grantee with `Grants.InviteGrantee {email, display_name}`. The server returns only an invitation id and status to the driver, never the code. It sends the one-time invite code to the invitation email address itself, so the code reaches only whoever controls that mailbox. This makes outbound mail a new server dependency. The grantee redeems the code with `Identity.RegisterGrantee {invite_code, idempotency_key}`. The request has no identity fields: the registered email and display name are taken solely from the invitation. The invite code is a random token of at least 128 bits from a cryptographic generator, and the server stores only its hash. The code is single-use. Once redeemed or accepted it is consumed, and a replay creates no second account. A replay with a different `idempotency_key`, or after 24 hours, also creates no new credentials. `RegisterGrantee` and `RegisterCustodian` also carry a client-generated `idempotency_key` of at least 128 random bits, so a lost response is recoverable. The server keeps, for 24 hours, the consumed code's hash with that key and the account it created, but never the credentials. A retry within 24 hours with the same code and the same key returns the same account id with a freshly issued access token and recovery code under the next `credential_generation` (the first response carries generation 1). Every generation issued stays pending until one is used. The first authenticated call with any generation's token activates that generation and revokes every other, and a retry after activation gets the uniform refusal. A recovery code works only with its own generation. `RecoverAccount` with a pending generation's recovery code activates that generation and revokes every other in the same transaction, then issues a new access token as recovery does today, so a delayed registration response from another generation is refused from then on. The client keeps the highest generation it has received, never makes an authenticated call with a lower one, and discards any registration response that arrives after its first authenticated call. A delayed response therefore cannot replace credentials the client is using, and whichever generation the client uses first is the one that works. A retry with the same code and a different key, or after 24 hours, gets the uniform refusal and changes nothing. The retry check runs before the unique-email check, so a valid retry is not refused because its own account already holds the address. Past that window, the account stays unusable until the host operator closes it with `rideaudit-admin account close --principal-id` (below), after which a new invitation can register the address again. Because `RegisterGrantee` is unauthenticated, it is rate-limited per source address and globally. Every failed redemption gets the same refusal, whether the code is unknown, expired, consumed or throttled, so no response shows whether a code exists. A failed attempt never consumes or locks a real invitation. `RegisterGrantee` and `RegisterCustodian` take no credentials; a call that presents any principal's credentials, including the inviting driver's, is refused. A grantee email is unique: `RegisterGrantee` refuses a code whose invitation email already belongs to a grantee account, creates no credentials, and leaves the code unused. A grantee who already has an account accepts a later invitation, from the same or another driver, with `Grants.AcceptInvitation {invite_code, idempotency_key}` under its own grantee credentials. That call succeeds only when the invitation's email equals the grantee's registered email; for anyone else it is refused and the code stays unused. The inviting driver learns who accepted through `Grants.ListInvitations` (below). The code expires, and it never appears in logs or in any response to the driver. Grant-use and refusal records name the grantee principal and its assurance level, `email-verified`. That level proves control of the invited address, not a real-world identity, and any attribution of a log to a named person is limited to that. The grantee receives a grantee principal, an access token and a recovery code, under the same credential rules as drivers. `Identity.RecoverAccount` works for grantees. `RecoverAccountResponse` gains `principal_kind` (`DRIVER`, `GRANTEE` or `CUSTODIAN`) and `principal_id`, which are additive fields under the same minor bump. For a driver, `principal_id` equals `driver_id`, and the existing fields are unchanged. For a grantee or a custodian, `driver_id` and `tenant_id` are empty, so no non-driver id is ever carried in a driver field. The inviting driver can call `Grants.DisableGrantee {grantee_id}`. This disables only the relationship between that driver and that grantee: it revokes that driver's grants and blocks new ones from that driver, and grants from other drivers are unaffected. Disabling the grantee account itself is reserved for the account owner, through `Identity.CloseAccount {}` (authenticated; it revokes the caller's tokens and recovery code, ends every grant naming the caller, and cannot be undone), or for the host operator with `rideaudit-admin account close --principal-id`. That is a host-local command under the same rules as the custodian commands. It has the effects of `CloseAccount`, including the refusal for a custodian that still holds an effective slot. A grantee with no live grant has no grant-scoped data access. The calls TR-RIDE-SEC-004 AC 7 authorizes independently of a grant still work for it. *Choice for Payton: driver-invited grantee accounts with server-sent email codes, as written here, or operator-provisioned ones where an operator verifies the identity. Either way, a code returned to the driver is not enough, because the driver could redeem it themselves (Codex review 5472895040).*
- **Grant management.** These calls take the driver principal only:
  - `Grants.IssueGrant {grantee_id, case_id, import_ids[], submission_ids[], operations[], expires_unix_millis}` returns `Grant`;
  - `IssueGrant` refuses a `grantee_id` that has not accepted an invitation from the caller, or whose relationship with the caller is disabled. *How a disabled relationship is restored (a new invitation, or never) is a choice for Payton;*
  - `Grants.RevokeGrant {grant_id}` returns `Grant`;
  - `Grants.ListGrants {}` lists the caller's issued grants;
  - `Grants.ListInvitations {}` lists the caller's own invitations: invitation id, email, display name, status (`pending`, `accepted` or `expired`) and, once accepted, the accepting `grantee_id`. It never returns the code. This is how the driver gets the `grantee_id` that `IssueGrant` needs.

  A grantee can call `Grants.ListMyGrants {}`. It returns grant id, grantor, case, operations, expiry and the granted `import_ids[]` and `submission_ids[]`, but no data.
- **Viewer authorization.**
  - `Grants.ResolveViewerRecords {grant_context?, records[{content_hash, receipt_core}]}` returns, per record, either a refusal reason, or the resolved submission id, its admission state, `receipt_core_digest` (the SHA-256 of the deterministic encoding of the `ReceiptCore` the custody journal holds), `ots_proof_digest` (the SHA-256 of the deterministic encoding of the `AnchorProofEnvelope` the custody journal holds for it, or empty when none is held), the authoritative case (the grant context's case on the Grantee path, none on the Driver path) and its stored sidecar commitment: `gps_present`, `obd2_present` and `telematics_digest`. The viewer re-encodes the bundle's telematics cues canonically and shows them only when the digest matches. `telematics_digest` is the SHA-256 of the deterministic proto3 encoding of `rideaudit.custody.v1.ReviewSidecarCues { repeated SidecarCue cues = 1; }`, where `SidecarCue { int64 session_offset_micros = 1; string kind = 2; string label = 3; }`. The cue list keeps recorded order, with no sorting or deduplication. `session_offset_micros` is the cue's session time in whole microseconds: the viewer converts its `TimeSpan` by `Ticks / 10`, and a time with leftover ticks is not representable, so its sidecars are withheld. `kind` and `label` are encoded as UTF-8 after Unicode NFC normalization, with no trimming or case folding. A zero cue list encodes as zero bytes, and its digest is the SHA-256 of the empty string. The device and viewer must produce identical bytes, so the contract ships golden vectors (cue lists with their expected encodings and digests) that every implementation tests against. It shows the GPS and OBD2 presence flags only when they equal the server's values. `grant_context` is absent on the Driver path.
  - **Sidecar commitment (ingest dependency).** Today the server never receives the telematics cues or the GPS and OBD2 flags. They exist only in the bundle (`ReviewRecord`), so the server has nothing to bind them to. The device's submission therefore adds `sidecar_commitment {telematics_digest, gps_present, obd2_present}`, which is stored with the submission in the custody journal and never rewritten. A submission without one, including every submission made before this change, has unbound sidecars. The viewer still shows its verified core and withholds the sidecars with reason `SIDECAR_UNCOMMITTED`.
  - `Grants.UploadViewerRefusals {entries[{client_event_id, at_unix_millis, grant_id?, record_hash, reason}]}` is idempotent by `client_event_id`.
- **Escrow binding.** This is a dependency of FR-RIDE-079 AC 5, on the court path:
  - `VerifyForCounsel` counts quorum only for a release whose key belongs to the requested submission's sealed record, grantor tenant and case, and whose requester is the authenticated caller. A quorum release that another principal requested for the same record and case is not reported as `EscrowQuorumMet` or `WorkingCopyAuthorized` to this caller;
  - `RequestCourtRelease` binds `requester_id` to the authenticated caller. A driver or grantee principal may request; a custodian may not. For a driver, today's check that the key's tenant equals the caller's tenant stays. A grantee has no tenant, so a grantee's request carries a `grant_id`. It is accepted only when that grant names the caller as grantee, is neither expired nor revoked when the request is made, names the release's case, lists the submission of the key's sealed record, and has a grantor whose tenant is the key's tenant. The grant only identifies the driver. It never authorizes the release, which still needs custodian quorum. A case id alone never identifies a driver, because two drivers may use the same case string. *Owner choice: whether the grant must still be live at request time; this spec says yes.* `RequestCourtRelease` also carries an `idempotency_key` under the rule in AC 8: a retry with the same key and the same request returns the same release id and creates no second pending record, and the same key with a different request is refused with `VALIDATION_FAILED`;
  - on the Driver path, `VerifyForCounsel` refuses a submission the caller does not own with `TENANT_ISOLATION`. Today it checks only that the caller is authenticated;
  - `ApproveCourtRelease` accepts only an authenticated custodian principal that is the effective holder of a slot on that key (see "Custodian principals");
  - `OpenExpiringWorkingCopy` opens only for the authenticated requester of that release, and only when the request's `sealed_record_id` equals the sealed record of that release's server-held key package. This is checked before any decryption. A release approved for record A never opens record B;
  - **Court authority.** The server cannot verify a court order: there is no court credential or PKI to check. Today `RequestCourtReleaseRequest` carries only a caller-supplied `legal_process_reference`. This candidate adds `legal_process_document_hash`, `idempotency_key`, and `grant_id` for a grantee requester. The authority is therefore the M-of-N custodian quorum, not the request. A request creates only a pending record, which binds the requester, key, case, `legal_process_reference` and a required `legal_process_document_hash` (SHA-256 of the court document, a new field). Each `ApproveCourtRelease` names that same document hash. Custodians verify the court document out of band before approving, and an approval whose hash differs is refused. Until quorum, the pending record grants no key material and no working copy. *This is an owner decision: custodian quorum as the court authority, or a stronger external credential.*
- **Custodian principals (court-path dependency).** Today escrow custodians are bare strings on the key. The server authenticates only `DriverPrincipal`, and `ApproveCourtRelease` trusts the request's `custodian_id`. This adds a third principal kind, custodian:
  - provisioning is not a network call. The repository authenticates only principals and has no operator principal or role (no RBAC, per the owner). So the host operator, meaning whoever can run the server's admin command on the server host as the account that owns its data directory, runs `rideaudit-admin custodian provision --email --display-name`. That sends a single-use code under the grantee-code rules and prints only the custodian id and status. No gRPC method provisions custodians, and no driver, grantee or custodian token can;
  - the custodian redeems it with `Identity.RegisterCustodian {invite_code, idempotency_key}`, which issues a custodian principal, an access token and a recovery code. `RecoverAccount` reports `principal_kind` `CUSTODIAN`;
  - emails are unique within each principal kind, but one address may belong to a driver, a grantee and a custodian at once. `RecoverAccountRequest {email, recovery_code}` is matched as a pair across every principal kind. Recovery codes carry at least 128 random bits and are stored hashed, so at most one account matches. A pair that matches no account gets the uniform refusal. Lookup order never decides which account recovers;
  - the custodian ids recorded on a new escrow key are custodian principal ids. When the key package is committed, each id is checked in the same transaction: it must be an existing, registered, active custodian principal, distinct from every other id on the key. Otherwise the key is not created. An escrow key created before this change names bare custodian strings, and those strings are never rewritten. The host operator binds each one with `rideaudit-admin custodian bind-legacy --key-id --legacy-name --custodian-id`, after verifying out of band that the principal is that custodian. In the same transaction as the binding record, the command checks `--custodian-id` with the key-creation rule: an existing, registered, active custodian principal. Otherwise nothing is appended. This appends a binding record to the custody journal. An approval counts only when the principal is the effective holder of a slot on that key (defined below). An unbound legacy name cannot approve, so quorum waits for the binding, and the key package stays intact;
  - before approving, a custodian reads the pending release with `Escrow.GetPendingRelease {release_id}`. It is callable only by a principal that is the effective holder of a slot on that release's key. It returns the requester, key id, sealed record id, submission id, case id, `legal_process_reference`, `legal_process_document_hash`, creation time and the approvals recorded so far by slot. That gives the custodian an authoritative target to compare with the court document. `ApproveCourtRelease` must echo the key id, sealed record id, case id and document hash the custodian approved. The server refuses the approval, and records nothing, if any echoed value differs from the pending release;
  - `ApproveCourtRelease` takes the custodian from the authenticated token. A request `custodian_id` that differs from it is refused. The approval counts only when that principal is the effective holder of a slot on the key;
  - legacy bindings are one-to-one per key. A principal may be the effective holder of at most one custodian slot on a key. Every new binding and every substitution is checked against the effective holders of all the key's slots, after all earlier bindings and substitutions are applied, so the order of operations cannot give one principal two slots. Quorum counts distinct custodian slots of the key. Each approval is recorded against the slot its principal represented when it approved, and one slot never counts twice;
  - the **effective holder** of each slot on a key is found by applying the key's legacy bindings and then its substitution records, in journal order, to the custodian named in the key package. The id still written in the package bytes does not count once a substitution has replaced it. One rule, this one, decides `GetPendingRelease`, `ApproveCourtRelease`, quorum counting and account closure. A replacement holder is authorized for its slot, and the replaced principal is no longer authorized for any of them. The same rule keeps requester and approver apart: `RequestCourtRelease` is refused when the requester is the effective holder of any slot on that key, and `ApproveCourtRelease` is refused when the approver requested that release. One person may hold a driver or grantee account and a custodian account under the same email, so separation also compares emails, trimmed and lower-cased as registration stores them: `RequestCourtRelease` is refused when the requester's email equals the email of any effective holder on the key, and `ApproveCourtRelease` is refused when the approver's email equals the requester's. A new escrow key needs a threshold of at least two slots. Residual risk: the server cannot link one person's accounts under different emails, so such a person can still approve their own request. On a key with a threshold of two or more, that approval still needs another custodian's, and custodians verify the court document out of band. *Owner choice: what happens to an existing key with a threshold of one.*;
  - a custodian cannot close its own account while it is the effective holder of a slot on any escrow key. `Identity.CloseAccount` refuses that custodian and changes nothing. Retiring such a custodian requires a replacement first. The host operator runs `rideaudit-admin custodian replace --key-id --old-custodian-id --new-custodian-id` after verifying the new person out of band, which appends a substitution record (the key package stays unchanged). The new principal must be an existing, active custodian principal (not unknown, not a driver or grantee, not closed), and it must not already represent another slot on that key. Otherwise the replacement is refused, nothing is appended, and the slot keeps its current holder. The substitution voids that slot's approvals on every release of the key that has not yet reached quorum. The new custodian must approve again, and the old principal's approval never counts beside the new one's. Once a custodian holds no effective slot, it may close its account;
  - a custodian token is accepted only by `Identity.CloseAccount`, `Escrow.GetPendingRelease` and `ApproveCourtRelease`. A custodian registers and recovers through calls that take no token: `Identity.RegisterCustodian`, which refuses any call that presents credentials (see "Public contracts"), and `RecoverAccount`, which identifies the account by email and recovery code. Every other RPC refuses a custodian token with `TENANT_ISOLATION`, returns no data, changes no state and writes a refusal record.

  *Choice for Payton, tied to the escrow defect fix (PR comment of 2026-10-09 16:17Z): operator-provisioned custodian principals as written here, or another custodian model.*

  The current master code does none of these (`GrpcServices.cs`, `EscrowGrpcService`). That is a pre-existing defect, reported separately on PR #29.

## Grantee authentication

r1 offered a bearer-secret option. Codex showed it contradicts a *named* grantee: possession of a secret cannot prove who is calling, and the use log would attribute a forwarded secret's use to the wrong person. r2 therefore specifies **grantee accounts** (TR-RIDE-SEC-004 AC 1).

If you prefer the bearer route anyway, the sentence and ACs must change so that the capability holder, not a named person, is the grantee, and logs must attribute use to the grant, not a person. That is a different AGREE.
